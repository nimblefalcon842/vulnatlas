CVE-2026-98260: A use-after-free of a POSIX CPU timer object across a failed exec

Independent verification report

VulnAtlas Research | 2026-11-20

Companion record: the 2026-11-17 deep-dive writeup for the same CVE stays published as its own page; this report is the full, gate-passed verification record.

Contribution statement: our contribution is independent verification only: own reproduction, own root-cause analysis and reverse-engineering confirmation in our own lab on Linux 6.6.157. The issue was found and disclosed by Hyunwoo Kim (V4bel), with public disclosure on the oss-security list on 16 October 2026. No priority claim is made.

1. Verdict

CVE-2026-98260 is a use-after-free of a POSIX timer object (k_itimer) in the Linux kernel’s POSIX CPU timer path, reachable from an unprivileged local process when a multithreaded child’s non-leader thread arms a per-thread CPU timer and its execve() fails after the point of no return.

Impact, the headline of this report: the demonstrated base impact is an uncontrolled local kernel crash, a GPF/Oops in the reaping path of a parent reaping an affected child, reproduced on a plain near-defconfig kernel with no special configuration (section 4.1). The escalation route, kernel memory corruption through the stale rbtree node if its page is reclaimed with attacker-influenced contents, is assessed feasible by our analysis (section 4.3) but was NOT demonstrated; external trackers rate the worst case at 7.8 High on that basis, and our published record carries 6.1 Medium (section 4.4). Every kernel from 5.7 up to the first fixed release on its line is affected (section 7). The upstream fix is commit acb03d3881818581052924a9bbbe92b8741ed448 (“exec: Cleanup POSIX timers right after de_thread()”).

Our verification evidence, all from our own lab:

  • Phase 1 (plain kernel, Linux 6.6.157 near-defconfig build): crash-only GPF/Oops on the analysis path (runs 14 and 16), plus a kill-delay sweep bounding the race window (the 100 us hit and the clean re-capture are observed runs in our lab logs; the 50 us no-hit point is a runbook sweep value, not a pinned lab observation).
  • Phase 2 (KASAN kernel, Debian 6.12.115+deb13.1-amd64 default-config build): a deterministic slab-use-after-free report, reproduced 3/3, with the full object lifecycle pinned by the report’s own alloc/free/read stacks (alloc task 846, free-executing task 803, reader task 57; three distinct task IDs support the multithreaded-child fact).

2. Technical background

POSIX CPU timers measure CPU time consumed by a process or thread. A timer created with timer_create(CLOCK_THREAD_CPUTIME_ID) is a per-thread timer: its k_itimer object (a 256-byte allocation from the dedicated slab cache posix_timers_cache) carries a cpu_timer node, and while the timer is armed that node is queued in the rbtree of the thread that armed it (the thread’s posix_cputimers structure). The kernel looks the task up by the PID stored on the timer.

Two properties of the surrounding machinery matter for the bug:

  • The k_itimer free is RCU-deferred: exit_itimers() queues the object onto an RCU callback, and rcu_core (softirq context) executes the actual kmem_cache_free() later. The window between the logical free and the physical free is asynchronous and not observable by the exiting task.
  • exec() exchanges thread identities: de_thread() swaps which task owns the leader PID. A per-thread CPU timer’s PID reference therefore changes meaning across de_thread(): the node stays queued on the original thread’s rbtree, but PID lookups for it now resolve differently.

3. Root cause: one chain, kill and exec are one event

Race anatomy (upstream record, verified against our own reproduction): a non-leader thread B of a multithreaded child arms a per-thread CPU timer (CLOCK_THREAD_CPUTIME_ID); the node is queued on B. B execve()s. de_thread(B) exchanges TIDs, so B’s PID now belongs to the leader. If the leader is reaped at this point, release_task(leader) -> posix_cpu_timers_exit(leader) cleans the leader’s queue, not B’s. The exec continues. Because bprm->point_of_no_return is set BEFORE de_thread(), any later failure path (unshare_files(), set_mm_exe_file(), exec_mmap() or exec_task_namespaces() failing, or a SIGKILL landing during the killable exec wait in exec_mmap()’s mmap_read_lock_killable()) brings the task down before begin_new_exec() reaches the cleanup. The unwind runs through get_signal() -> do_exit() -> exit_itimers(), which frees the k_itimer (posix_timer_delete() -> posix_cpu_timer_del() -> posix_timer_unhash_and_free(), and the deferred kmem_cache_free()) while its node is still queued: exit_itimers() SKIPS the disarm of the queued node here. That is the bug.

The parent’s wait4() reaping then runs release_task() -> posix_cpu_timers_exit() -> timerqueue_del() on the freed node: a use-after-free.

In the normal (success) case the state stays invisible because begin_new_exec() calls posix_cpu_timers_exit(me) right after exec_task_namespaces(), which removes the leftover node. Only the failing-exec unwind reaches the bug; a plain (non-exec) exit cannot reach it, per the upstream record and our own driver design.

Proof of the exec precondition in our runs is the observed timer_lock_sighand() failed-lookup WARNING (kernel/time/posix-cpu-timers.c:564), which fires when the node is still queued but the PID lookup fails - not the free stack, whose exec frames are already gone after the -EINTR unwind.

The fix

acb03d388181 (“exec: Cleanup POSIX timers right after de_thread()”, fs/exec.c, +21/-8; Signed-off-by Hyunwoo Kim and Thomas Gleixner; Reviewed-by Oleg Nesterov and Frederic Weisbecker; Cc: stable) does not add a barrier at exit or harden the reap-time walk. It creates a helper posixtimer_exec() - posix_cpu_timers_exit(me) + exit_itimers(me) + flush_itimer_signals() under the sighand siglock, gated on CONFIG_POSIX_TIMERS - and calls it in begin_new_exec() immediately after de_thread() returns success, removing the identical cleanup block from its old, later position. The commit message states the requirement: the cleanup must run there so that CPU timers armed on the current task are dequeued before any post-point_of_no_return failure path can bring the task down; after the TID switch, a later deletion of the timer would not remove an enqueued timer because the old-TID lookup fails.

4. Impact analysis

4.1 Confirmed impact: local kernel crash

The demonstrated trigger is a use-after-free read. On the plain (non-KASAN) 6.6.157 build it presents as a GPF/Oops in the reaping path:

Oops: 0002 [#1] PREEMPT SMP NOPTI
  timerqueue_del+0x2e/0x70
  posix_cpu_timers_exit+0x8d/0xc0
  release_task+0xf3/0x500
  ...

The crash path is the parent reaping an exited child: release_task() -> posix_cpu_timers_exit() -> timerqueue_del() dereferences the freed node’s rbtree fields.

The fault signature is heterogeneous across runs in our groom campaign: GPF (RDX = 0x004a801d00000000, faulting access [RDX+0x10]), page-fault not-present, and NULL-deref variants, with fault CLASS varying while fault RATE stays deterministic (1/1 on the direct driver, 4/4 on the groom variant in the recorded campaign). The heterogeneity is itself the fingerprint of uncontrolled reuse: what the freed object’s rb fields hold depends on what the slab has done with the memory since.

4.2 The KASAN record

On the Debian default-config 6.12 build the same sequence yields a deterministic slab-use-after-free report, reproduced 3/3 (excerpted from our lab log):

BUG: KASAN: slab-use-after-free in timerqueue_del+0x100/0x130
Read of size 8 at addr ffff888003a04078 by task trigger98260/57
  timerqueue_del+0x100/0x130
  posix_cpu_timers_exit+0x180/0x240
  release_task+0x244/0x13a0
Allocated by task 846: ...
Freed by task 803:
  exit_itimers+0x347/0x620 -> __call_rcu_common
  ... (executed later by rcu_core, kmem_cache_free)
The buggy address belongs to the object at ffff888003a04000
  which belongs to the cache posix_timers_cache of size 256

The free stack’s do_group_exit() -> do_exit() -> exit_itimers+0x347 -> __call_rcu_common is the tail of the SAME chain as the upstream exec-failure path - the non-leader thread fails execve on a late failure path, the exec unwinds (-EINTR), the delayed kill lands during the killable exec wait. Kill and exec are one chain. The log’s second exit_itimers frame (+0x4b5, with posix_cpu_timer_del) is the same teardown event’s disarm/delete call site, not a second free path.

4.3 Escalation potential (analytic, not demonstrated)

Escalation potential: plausible but undemonstrated. The demonstrated primitive is a UAF read; byte-level controlled data was NOT demonstrated in our attempts.

Chain to maximum demonstrated impact, weakest prerequisite to strongest demonstrated effect: an unprivileged local process (no capability, no module load, no sysctl) -> a multithreaded child whose non-leader thread arms a per-thread CLOCK_THREAD_CPUTIME_ID timer -> an exec made to fail after the point of no return (SIGKILL landing in the killable exec wait) -> a parent reaping inside the RCU-free window -> strongest demonstrated impact: a deterministic use-after-free read that presents as an uncontrolled local kernel crash (GPF/Oops on the plain kernel; the same read under KASAN as the slab-use-after-free report of section 4.2). Everything past that ceiling is analytic, not demonstrated (the cross-cache route below).

We characterized the reclaim behaviour directly (source reads plus recorded groom runs):

  • Same-cache reclaim (spraying fresh timer_create() allocations): hits the right cache (posix_timers_cache) but cannot carry attacker bytes into the freed object. The cache is a dedicated kmem_cache and the allocation path is kmem_cache_zalloc(): a reclaiming CLOCK_MONOTONIC timer zeroes its hrtimer, including the embedded timerqueue node, at init; and sigev_value is stored outside k_itimer, in the separate sigqueue object (kernel/time/posix-timers.c:489 in the published 6.6.157 source). Same-cache reuse therefore yields deterministic kernel-written (zero) contents at the rb offsets: a clean deterministic-reuse demonstration, never attacker-chosen bytes.
  • System-V message-queue sprays (msgsnd-class objects) structurally cannot reclaim a k_itimer at all: the spray objects land in a kmalloc bucket, the victim lives in the dedicated posix_timers_cache. Our own first groom design made this mistake and we record it here as a negative result: the 0x41 “misses” were a cache mismatch, not tuning noise.
  • Attacker-chosen bytes require cross-cache page-level reclaim: drain the victim’s slab page (all k_itimers on it freed, so SLUB releases the page back), wait out the RCU-deferred frees, then page-fill spray with controlled content. Assessed feasible; it requires a page-drain churn design, an RCU-aware spray window (spray AFTER the rcu_core callback, not a fixed delay), and page-order-matched spray sizing. We have NOT performed this; the config is parked in our lab.

External corroboration of the framing: Red Hat’s statement for the CVE reads “The confirmed impact is a local kernel crash. The stale rbtree node also provides a plausible memory corruption condition that may permit privilege escalation if the freed allocation is reused with attacker influenced contents.” (Red Hat CVE database, live-read 2026-11-19.)

4.4 Severity

Our published record carries CVSS 3.1 6.1 Medium (AV:L/AC:L/PR:L/UI:N/S:U/C:L/I:N/A:H), anchored on the demonstrated impact (uncontrolled local kernel crash). External trackers rate the same primitive higher on the confidentiality/integrity axes: the Linux CNA and NVD rate 7.8 (AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H), SUSE rates 7 (v3, AC:H variant) and 7.3 (v4), Red Hat rates 7.0, and the public PoC writeup’s table carries 7.8 High. The divergence is exactly the controlled-data question in 4.3: the external scores price the escalation route our analysis assesses feasible but does not demonstrate, and our score stays anchored on what is demonstrated. Both readings are recorded here as their sources state them.

5. Production reachability

Per the finding-template reachability field:

  • Is the vulnerable code path reachable in the default/production config? YES. POSIX timers are enabled by default (CONFIG_POSIX_TIMERS=y in defconfig); reaching the path takes only unprivileged syscalls: timer_create(), timer_settime(), a failing execve, kill, and a parent waiting in wait4(). No capability, no module load, no sysctl.
  • Which custom Kconfig/module param/distro setting is required? NONE for the bug. Our plain lab build is x86_64_defconfig with build-practical tweaks only (CONFIG_MODULES=n, CONFIG_DEBUG_INFO_BTF=n, CONFIG_SYSTEM_TRUSTED_KEYS unset, CONFIG_DEBUG_INFO_NONE=y, CONFIG_SERIAL_8250_CONSOLE=y); none gate the vulnerable path. The KASAN runs ran on a Debian default-config 6.12 build (6.12.115+deb13.1-amd64) and reproduced 3/3.
  • Does the trigger hit in the default config? YES. The crash-only GPF/Oops reproduced on the plain near-defconfig kernel; KASAN is a debug-only amplifier for detection, not a requirement for the bug.
  • Trigger shape: a MULTITHREADED child whose NON-LEADER thread arms the per-thread CPU timer and execve()s (forced to fail). A single-threaded child or a plain exit does not reach the path.
  • Open check item: distro variance in posix-cpu-timer knobs (e.g. CONFIG_POSIX_CPU_TIMERS_TASK_WORK) to be confirmed against the upstream fix; it does not change the YES.

6. Reproduction methodology overview (sanitized)

Pseudocode only: this is not a runnable program and not a working exploit. The runnable lab driver stays private and is available to maintainers on request.

  1. A parent forks a MULTITHREADED child (at least two threads); the parent later waits in wait4() to reap it.
  2. The child’s NON-LEADER thread calls timer_create(CLOCK_THREAD_CPUTIME_ID, …) + timer_settime(): the per-thread CPU timer is what queues the k_itimer’s cpu_timer node on THAT thread’s posix_cputimers rbtree. Any other clock leaves the node out of that rbtree and the described read becomes impossible.
  3. That thread execve()s, and the exec is made to fail after the point of no return. The concrete mechanism, ours and the one documented in the upstream record, is delivering SIGKILL to that thread (tgkill on the non-leader thread’s TID) while it sits in the killable wait inside exec_mmap()’s mmap_read_lock_killable(): the exec unwinds with -EINTR, the signal is then taken through get_signal -> do_exit -> exit_itimers(), which frees the k_itimer while its node is still queued; rcu_core later executes the kmem_cache_free().
  4. The parent’s wait4() reaping runs release_task() -> posix_cpu_timers_exit() -> timerqueue_del(), which reads the timerqueue node of the already-freed k_itimer when reaping lands inside the RCU-free window.

Race window control: the observable window is between the child’s exit and the RCU grace period that executes the deferred free. The lab driver paces reaping with a microsecond-scale kill-delay sweep to land wait4() inside that window deterministically. Tuning parameter values stay out of this description and remain in the private driver only.

Demo: the demo artifact is the plain-kernel recording, demo98260_v2_nokasan.cast (about 31 seconds of playback, GPF at about 17 seconds in), showing the real GPF oops on the 6.6.157 plain build on the exact analysis path: RIP rb_next, call trace timerqueue_del <- posix_cpu_timers_exit <- release_task <- wait_consider_task <- do_wait <- wait4. The KASAN recording is retained as the attribution artifact (the slab-UAF report), not as the demo.

Lab builds: Linux 6.6.157 own build (x86_64_defconfig plus build-practical tweaks; source pinned to kernel.org linux-6.6.157.tar.xz, published sha256 b74a43d0630809b7871cc906ac155e956cbc0b2e78a7451f5e6c8bfcb1208c30) and a Debian 6.12.115+deb13.1-amd64 default-config build for the KASAN runs. All lab work loopback/local on our own VMs.
