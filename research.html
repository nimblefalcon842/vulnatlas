CVE-2026-98260: a use-after-free of a POSIX CPU timer object across a failed exec

VulnAtlas Research | 2026-11-17

VulnAtlas Research | 2026-11-17

The issue was found and disclosed by Hyunwoo Kim (V4bel), with public

disclosure on oss-security on 16 October 2026. This writeup makes no

priority claim: my contribution is independent verification only, my own

reproduction, root-cause analysis and reverse-engineering confirmation on

Linux 6.6.157.

1. Verdict

CVE-2026-98260 is a use-after-free of a POSIX timer object (k_itimer) in

the Linux kernel timer subsystem, reproduced in my local lab on Linux

6.6.157.

  • Phase 1 evidence: crash-only GPF/Oops on the plain kernel (runs 14 and

16), and a deterministic kill-delay sweep bounding the race window

(100 us hit and the clean re-capture hit are observed runs pinned in my

lab logs; the 50 us no-hit point is a runbook sweep value, not a pinned

lab observation).

  • Phase 2 evidence: a KASAN kernel run with a slab-use-after-free report,

slab-use-after-free in timerqueue_del(), Read of size 8, with the full

object lifecycle pinned by the report's alloc/free/read stacks (alloc

task 846, free-executing task 803, reader task 57; three distinct task

IDs support the multithreaded-child fact).

Fix attribution (live-verified): Hyunwoo Kim (V4bel) + Thomas Gleixner

series; fix commit acb03d3881818581052924a9bbbe92b8741ed448, cited from

its own commit message (V3 posting, Sep 11 patch email), which carries the

full race anatomy. Thomas Gleixner's LKML series "[patch V2 0/8]

exec/exit: POSIX timer related bugfixes" (Sep 5-7, Frederic Weisbecker

review) is the public discussion context for the mechanism; the commit

message itself is the mechanism record this analysis cites.

2. Mechanism: one chain, kill and exec are one event

Race anatomy (upstream record, one chain): a non-leader thread of a

multithreaded child arms a per-thread CPU timer (CLOCK_THREAD_CPUTIME_ID)

and execve()s; the exec fails on a late failure path and unwinds (-EINTR);

the delayed kill lands during the killable exec wait and the unwind

continues through get_signal -> do_exit -> exit_itimers, which frees the

k_itimer while its node is still queued. exit_itimers() here SKIPS the

disarm of the queued node (the bug); the parent's wait4() reaping then

runs posix_cpu_timers_exit() -> timerqueue_del() on the freed node.

Reaching the bug from a plain (non-exec) exit is not possible per the

upstream record; my lab reproduced the exec-failure variant. Proof of the

exec precondition is the driver design plus the observed

timer_lock_sighand failed-lookup WARNING

(kernel/time/posix-cpu-timers.c:564), not the free stack; exec frames are

absent from the free stack because the exec unwind has already completed

after -EINTR.

The fix, acb03d388181 ("exec: Cleanup POSIX timers right after

de_thread()", fs/exec.c, +21/-8; Signed-off-by Hyunwoo Kim and Thomas

Gleixner; Reviewed-by Oleg Nesterov and Frederic Weisbecker; Cc: stable),

does not add a barrier at exit or harden the reap-time walk. It creates a

helper posixtimer_exec() (posix_cpu_timers_exit(me) + exit_itimers(me) +

flush_itimer_signals() under the sighand siglock, gated on

CONFIG_POSIX_TIMERS) and calls it in begin_new_exec() immediately after

de_thread() returns success, removing the identical cleanup block from its

old, later position. The comment states the requirement: the cleanup must

run there so that CPU timers armed on the current task are dequeued from

me::posix_cputimers before any post-point_of_no_return failure path

(unshare_files(), set_mm_exe_file(), exec_mmap(),

exec_task_namespaces()) can bring the task down; after the TID switch, a

later deletion of the timer would not remove an enqueued timer because the

old-TID lookup fails.

3. What my lab pinned

  • Crash-only GPF/Oops on the near-defconfig plain kernel (runs 14, 16).
  • Kill-delay sweep bounding the window; the working sweep point and the

re-captured full splat are pinned in my lab logs.

  • Phase 2 KASAN run: slab-use-after-free, faulting access

timerqueue_del(), Read of size 8 (timerqueue-node read). The free is an

RCU-deferred free queued from exit_itimers() at process exit and

executed later by rcu_core (kmem_cache_free). The reader is the reaping

path: release_task() -> posix_cpu_timers_exit() -> timerqueue_del(),

i.e. a parent in wait4() reaping an exited child that created a POSIX

timer via timer_create().

  • do_group_exit provenance: the free stack's do_group_exit -> do_exit ->

exit_itimers+0x347 -> __call_rcu_common (the deferred-free queue) is the

tail of the SAME chain as the upstream exec-failure path, not a separate

kill variant: the non-leader thread fails execve on a late failure path,

the exec unwinds (-EINTR), and the delayed kill lands during the

killable exec wait. Kill and exec are ONE chain.

  • Pinned stack: exit_itimers+0x347 -> __call_rcu_common, because the

reader's UAF dereferences the node after the RCU-deferred free that

chain queues. The log's second exit_itimers frame (+0x4b5, with

posix_cpu_timer_del) is the same teardown event's disarm/delete call

site, not a second free path.

4. Production reachability

  • Is the vulnerable path reachable in the default/production config? YES.

POSIX timers are enabled by default (CONFIG_POSIX_TIMERS=y in

defconfig); reaching the path takes only unprivileged syscalls:

timer_create(), timer_settime(), a failing execve, kill, and a parent

waiting in wait4(). The reaching exit is a FAILING-exec unwind; a plain

exit does not reach the path. No capability, no module load, no sysctl.

  • Which custom Kconfig/module param/distro setting is required? NONE for

the bug. The plain lab build is x86_64_defconfig with build-practical

tweaks only (CONFIG_MODULES=n, CONFIG_DEBUG_INFO_BTF=n,

CONFIG_SYSTEM_TRUSTED_KEYS unset, CONFIG_DEBUG_INFO_NONE=y,

CONFIG_SERIAL_8250_CONSOLE=y); none gate the vulnerable path. The KASAN

runs ran on a Debian default-config 6.12 build (6.12.115+deb13.1-amd64)

and reproduced 3/3.

  • Trigger shape: a MULTITHREADED child whose NON-LEADER thread arms the

per-thread POSIX CPU timer and execve()s (forced to fail). A

single-threaded child or a plain exit does not reach the path.

  • Does the trigger hit in the default config? YES. The crash-only

GPF/Oops reproduced on the plain near-defconfig kernel; KASAN is a

debug-only amplifier for detection, not a requirement for the bug.

  • Open check item: distro variance in posix-cpu-timer knobs (e.g.

CONFIG_POSIX_CPU_TIMERS_TASK_WORK) to be confirmed against the upstream

fix; does not change the YES.

5. Trigger description (sanitized)

Pseudocode only: this is not a runnable program and not a working exploit.

The runnable lab driver stays private and is available to maintainers on

request.

1. A parent forks a MULTITHREADED child (at least two threads); the

parent later waits in wait4() to reap it.

2. The child's NON-LEADER thread calls

timer_create(CLOCK_THREAD_CPUTIME_ID, ...) + timer_settime(): the

per-thread CPU timer is what queues the k_itimer's cpu_timer node on

THAT thread's posix_cputimers rbtree. Any other clock leaves the node

out of that rbtree and the described read becomes impossible.

3. That thread execve()s and the exec is forced to FAIL on a late failure

path; the unwind returns -EINTR and a delayed kill lands during the

killable exec wait; the unwind then runs through get_signal -> do_exit

-> exit_itimers(), which frees the k_itimer while its node is still

queued; rcu_core later executes the kmem_cache_free().

4. The parent's wait4() reaping runs release_task() ->

posix_cpu_timers_exit() -> timerqueue_del(), which reads the timerqueue

node of the already-freed k_itimer when reaping lands inside the

RCU-free window.

Race window control: the observable window is between the child's exit

and the RCU grace period that executes the deferred free. The lab driver

paces reaping with a microsecond-scale kill-delay sweep to land wait4()

inside that window deterministically. Tuning parameter values stay out of

this description and remain in the private driver only.

Demo: the demo artifact is the plain-kernel recording,

demo98260_v2_nokasan.cast (about 31 seconds of playback, GPF at about

17 seconds in), showing the real GPF oops on the 6.6.157 plain build on

the exact analysis path: RIP rb_next, call trace timerqueue_del <-

posix_cpu_timers_exit <- release_task <- wait_consider_task <- do_wait

<- wait4. The KASAN recording is retained as the attribution artifact

(the slab-UAF report), not as the demo.

6. Affected range and stability checks

  • Introduced by 55e8c8eb2c7b6bf30e99423ccfe7ca032f498f59 ("posix-cpu-timers:

Store a reference to a pid not a task", Eric W. Biederman; itself fixing

e0a7021), i.e. v5.7.0.

  • Fixed per stable line: 6.1.191 / 6.6.158 / 6.12.112 / 6.18.54 / 7.2.8;

mainline 7.3. Every kernel from 5.7 up to the first fixed release on its

line is affected; there is no pre-5.7 exposure. My reproduction tree,

6.6.157, sits one patch below the 6.6-line fix.

  • Fix lineage (all three commits fresh live-read): 55e8c8eb2c7b (v5.7) ->

920f893 + a73d7f9 (Jul 5 2026, CVE-2026-64560, Oleg Nesterov) ->

acb03d388181 (Sep 16 2026, complete fix) -> stable backports Oct 3 ->

the timers-core-2026-10-20 cleanup pull (merge aaf3d47, Oct 21).

  • 6.1.191 line-fix claim verified: the kernel.org changelog

ChangeLog-6.1.191 carries "exec: Cleanup POSIX timers right after

de_thread()" with [ Upstream commit

acb03d3881818581052924a9bbbe92b8741ed448 ]. The stable backport commit

6f1977cea3e85cd8ab55fb337d3e1725fe61d1ce (Hyunwoo Kim, Sep 11 2026) is

9. Safety, scope and public status

  • Not in CISA's Known Exploited Vulnerabilities catalog (checked against

the catalog feed released 2026-11-13); I have observed no exploitation

in the wild.

  • Crash-only research finding: the demonstrated trigger is a UAF read;

byte-level controlled data was NOT demonstrated in my attempts (three

cross-cache reclaim attempts plus a marker run did not place attacker

bytes at the read offset; the non-canonical freelist-pointer

dereference observed on the plain kernel is itself plain-kernel UAF

evidence). No exploit development, no weaponization, no gadget or

escalation-chain discussion.

  • All lab work loopback/local on my own VMs.
  • Public status: disclosed publicly on oss-security on 16 October 2026

(V4bel / Hyunwoo Kim), with a public PoC writeup on 26 October and

public repositories around the same date (noted as existence only, not

verified). I know of no in-flight duplicate on this root cause;

acb03d388181 remains the sole fix. The July 19-20 2026 mass-fix window

does not cover this area (the POSIX-timer CPU-timer paths are untouched

by it). This writeup is an independent-verification record, not a first

report; no priority claim is made.

  • Severity: CVSS 3.1 6.1 Medium (AV:L/AC:L/PR:L/UI:N/S:U/C:L/I:N/A:H).
